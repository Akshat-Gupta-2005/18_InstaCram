# DECISIONS — InstaCram

Append-only record of choices made and problems solved.
Current state lives in [FEATURES.md](FEATURES.md).

> **On the dates below.** Every entry dated 2026-09-11 was *recorded* on that date, during the documentation pass that produced these files. The decisions themselves were reached earlier, across the planning conversation whose reasoning trail is preserved in [_plan.md](_plan.md) §10. The order within the log follows the order they were decided, not the order they were written down.
>
> This file is never edited. If something here turns out to be wrong, a new entry is added saying so and pointing back at the old one.

---

## Decisions log

| Date | Decision | Why |
|---|---|---|
| 2026-09-11 | Position the product as **priming + revision**, not as learning from zero | The original framing — "people will absorb concepts subconsciously by scrolling" — does not survive contact with the fluency illusion (familiarity mistaken for retention). What *does* hold up is a narrower claim: brief prior exposure means you are not starting cold when a concept resurfaces. That claim has a concrete supporting case (see P2). Narrowing the claim is what makes the rest of the design honest. |
| 2026-09-11 | Content is **generated from scraped material, never served verbatim** | Scraping and republishing third-party text is a straightforward copyright problem. Using the scrape as grounding context and shipping generated prose plus the source URL keeps the grounding benefit without the republishing exposure. See P1. |
| 2026-09-11 | **Topics that do not reduce to one page are out of scope** for v1 | The one-page format is the entire product. A topic with real multi-step reasoning either gets mutilated to fit or breaks the format. Deferring the whole class of content is more honest than shipping bad cards for it. |
| 2026-09-11 | **No topic sequencing or prerequisite model** in v1 | A curriculum graph is a substantially different product with its own data model. v1 is a flat, field-scoped feed. Deferring it is a scope decision, not an oversight — but it has a consequence, see P6. |
| 2026-09-11 | **Decouple Topic identity from Field** via a `Field_Topic` many-to-many junction table | A topic is a concept, not a property of the field that happened to request it first. Modelling it as owned by a field forces regeneration of identical content per field. The junction table is what makes cross-field reuse possible at all. See P3. |
| 2026-09-11 | Cache check happens at **topic level, before generation**, not at field level | Per-field caching only helps a repeat request for the same field, which is the rare case. Per-topic caching helps every overlapping field, which is the common one. |
| 2026-09-11 | **Strict-threshold name-embedding matching only** — no meaning-disambiguation stage in v1 | ★ The two failure modes are not equally bad. A false merge silently serves the wrong concept under a field, with no error and no detection. A false split just regenerates something that already existed — wasted spend, nothing corrupted. So the threshold is biased toward splitting. The full two-stage solution is specified and deferred until real data shows bad merges actually happening. See P4. |
| 2026-09-11 | Fact-check failures are **deleted outright — no retry, no re-queue** | Retry logic means a queue, backoff, a poison-message policy and a dead-letter path: real machinery before there is any evidence the failure rate justifies it. Deleting is the simplest thing that cannot produce a wrong card. Its failure mode is known and accepted, see P10. |
| 2026-09-11 | Cards **stream to the client as each one passes fact-check**, rather than as a completed batch | On a cache miss the full pipeline is several LLM calls plus a scrape per topic. Batching means the user stares at nothing until the slowest card finishes. Streaming makes cold start tolerable. Consequence: card order becomes non-deterministic, which is only acceptable because v1 has no sequencing (see the deferral above). |
| 2026-09-11 | **Log every card view from day one, with no feature reading it** | View history cannot be backfilled. Every retention feature later considered — spaced resurfacing, coverage map, weekly recap, confidence scheduling — needs history that starts before the feature exists. Writing an unread table costs almost nothing; recreating the data costs everything. See P7. |
| 2026-09-11 | Ship **source link, trust label, bookmark, recall prompt, and "why this matters"** inside the MVP rather than after it | Each is near-zero cost as a schema field now and expensive to retrofit once content exists. Two of them are load-bearing rather than cosmetic: without the recall prompt the "revision tool" claim is aspirational, and without source link + trust label the content-trust problem has no answer at all. |
| 2026-09-11 | **Split the backend into two services** — Node serving, Python pipeline | Not a language preference. The read path must be fast, available, and boring; the pipeline is slow, bursty, and allowed to fail per-topic. Different scaling and failure profiles is the actual reason. Accepted cost: two toolchains, two test setups, two deployment units. |
| 2026-09-11 | **Node + Express + TypeScript** for the serving service | Most existing author experience (4+ prior projects). The read path is the half that should carry the least risk, so the risk budget goes to the pipeline instead. |
| 2026-09-11 | **Python + FastAPI** for the generation pipeline | The pipeline is scrape + multiple LLM calls + fact-check per topic — all I/O-bound and parallelisable. Async-native runtime is the deciding factor. |
| 2026-09-11 | **LangGraph** for agent orchestration | The pipeline contains a genuine branch (fact-check pass → persist, fail → delete), not a linear chain. An explicit graph model fits it directly. Prior working experience exists (TreasuryPulse). |
| 2026-09-11 | **LiteLLM, self-hosted as its own gateway**, with Gemini as the default | Requirement was an explicitly swappable provider with fallback. Routing both services through one OpenAI-compatible endpoint makes the model a config value rather than a code dependency, and gives cross-provider fallback without writing it. |
| 2026-09-11 | Leave the **final LLM provider undecided** on purpose | Model quality and pricing move faster than this project will. The gateway exists precisely so this stays a config line. Gemini is the working default, not a commitment. |
| 2026-09-11 | **Self-hosted Qdrant** for both vector collections | A managed-only vector service cannot run on a laptop or in a local `kind` cluster without an account and a network dependency, which breaks "clone and run" and adds a recurring cost floor. Qdrant has usable Python *and* Node clients, which matters because both services touch vectors. |
| 2026-09-11 | **Two separate vector collections**, not one | They are written and read at different times by different services for different purposes: topic-name vectors are written at topic creation and read on every lookup; scroll-content vectors are written per card and read by nothing in v1. Merging them would couple a hot dedup path to a cold search index. |
| 2026-09-11 | **Postgres table for the view log; Redis explicitly not the system of record** | Redis is a plausible later cache layer. Making it the store of record for the one dataset that cannot be reconstructed would risk losing exactly that data. Simplicity first, and the fallback position is the safe one. |
| 2026-09-11 | **Firebase Auth**, with hand-rolled JWT/RBAC deferred to phase 2 | Already implemented once (GoRide). Auth is not where this project is trying to be interesting; buying it back preserves time for the pipeline. Deferred, not rejected. |
| 2026-09-11 | **Playwright** for scraping *and* browser E2E testing | Both jobs need a driven browser. One library covering both is one dependency, one API to learn, one thing to keep working. |
| 2026-09-11 | **GKE over AWS EKS** — decided on a live pricing check, not preference | EKS charges a flat ~$0.10/hr (~$73/mo) control-plane fee with no free-tier equivalent. GKE carries a standing $74.40/month credit covering one zonal cluster's management fee. For a continuously-running personal project that is ~$73/mo versus ~$0/mo. Secondary: the author already has deep AWS experience (CVMS), so GCP adds breadth rather than repeating it. A local `kind`/`minikube` cluster stays a zero-cost fallback on identical manifests. |
| 2026-09-11 | **Streaks and daily goals deliberately excluded** | They sit in direct tension with the stated reason the project exists — reducing dependence on engagement-loop apps. Recorded explicitly so that if they are ever added it is a decision someone argued for, not a pattern that crept in because it is familiar. See P8. |
| 2026-09-11 | **Followed/curated feeds and community voting pushed out of scope**, not merely deprioritised | They convert a personal tool into a multi-user content platform, which brings moderation, trust and abuse problems that have nothing to do with the current design. That is a pivot, not a feature toggle, and it should be recognised as one before anyone starts it. |
| 2026-09-11 | Docs use the name **InstaCram**; "Microlearn" in [_plan.md](_plan.md) and the architecture diagram is superseded | InstaCram is the repo name and carries the positioning in the word itself — Instagram's format, cramming's purpose, which is exactly the priming/revision scope. Treated as provisional: if it changes, a new row is added here rather than these files being rewritten silently. |
| 2026-09-11 | Frontend frameworks (React Native/Expo, Next.js) recorded as **proposed, not decided** | They were inferred from prior project history and never actually agreed in the planning conversation. Writing them into the stack table as decided would manufacture a decision nobody made. Flagged as an open item instead. |
| 2026-09-11 | **Corrects the cost estimate in P9.** Emitting a description alongside each candidate name was described in P9 as "a real trade, not a free one". Costed: ~20 candidates × ~20 output tokens ≈ **400 output tokens per field request**. | That is negligible against the several LLM calls per topic that a single cache miss triggers. The estimate was made without being costed, and it was the main argument against the option it was attached to. Recorded rather than edited, because P9 is history and the changed number is the point. |
| 2026-09-11 | **Resolves P9.** The Topic-Name Vector DB embeds **name + a one-line description**, and the description that gets embedded is the one the Candidate Topic Generator emitted at query time — on a cache miss, that same one-liner is stored as the new topic's description. | Symmetry is the whole reason. Embedding a bare name against a name+description vector is asymmetric and depresses scores, which lands hardest on exactly the strict threshold the reuse design depends on. Making both sides come from the same model, the same prompt and the same length budget is what makes cosine distance mean something. Alternative A (index the name alone) was symmetric and free but makes P4 unwinnable — two bare "Stack" strings embed *identically*, not merely closely, so no threshold can separate them. Secondary benefit: this supplies P4's deferred disambiguation stage with the descriptions it would otherwise have to go and fetch. |
| 2026-09-11 | **New invariant:** the embedded description is always the candidate-generator one-liner and is never rewritten. Any richer human-facing description is a separate column that is never embedded. | Without this rule the previous decision quietly decays. Someone improves a description six months in, its vector shifts, and every similarity score involving that topic changes with no visible cause and no failing test. The constraint is what makes same-producer symmetry hold over time, not just on day one. |
| 2026-09-11 | **Threshold calibration method:** build a hand-labelled set of ~50 candidate pairs across deliberately overlapping fields (*Java Utils* / *Java Collections* / *DSA*) and deliberately colliding ones (*Web Development* / *DSA*, both yielding "Stack"), sweep the threshold, and **take the lowest value at which false merges = 0**, accepting whatever split rate results. | Encodes the P4 asymmetry in the calibration procedure itself rather than leaving it to whoever picks the number later. Also runs on the candidate generator and an embedding model alone — no pipeline, no scraper — so it can be done during P1 instead of waiting on P3. |
| 2026-09-11 | **Resolves P10.** Three parts: per-topic pass/fail counters, a `Topic.status` field (`pending` / `ready` / `empty`), and a separate quarantine table holding rejected draft text. | Each covers a different failure. Counters make the rejection rate a number someone can look up. `status` makes the zero-card topic representable — without it an empty topic is indistinguishable from a healthy one whose cards have not loaded, *and* the lookup treats it as a valid cache hit, so the failure is cached and served as success forever (a consequence of no-retry and topic-reuse combining, which neither decision produces alone). The quarantine table is the difference between detection and diagnosis: an over-strict fact-checker and a bad card generator produce the identical rejection number, and only the rejected text separates them. |
| 2026-09-11 | Quarantined drafts live in a **separate table**, never as a flag on `Scroll` | A boolean on the main table is one forgotten `WHERE` clause away from serving unverified content to a user. The entire purpose of the fact-check gate is that this cannot happen, so the guarantee should be structural rather than dependent on every future query being written correctly. |
| 2026-09-11 | The no-retry decision is **not reversed** — it is made observable | Option D (retry once at a higher temperature) was available and declined. Reversing a decision before the data that would justify it exists is how the original reasoning gets lost. The counters exist precisely so that reversal becomes an evidence-based decision later. |
| 2026-09-11 | **Resolves P11.** Four parts: Postgres-first write order, a **transactional outbox**, a two-way reconciliation check, and a `reindex` command that rebuilds Qdrant from Postgres. | The outbox is the actual fix — topic row and outbox row commit in one Postgres transaction, a worker drains the outbox into Qdrant, so a vector write can fail and retry without the topic ever being lost. Write order still matters for anything outside the outbox path, and Postgres-first is chosen on the same asymmetry as P4: it fails toward *waste* (an invisible topic that regenerates) rather than *corruption* (an orphan vector that matches a lookup and then resolves to nothing, turning a reported cache hit into a serving error). Reconciliation is retained as a safety net rather than the primary mechanism. |
| 2026-09-11 | `reindex` is built regardless of P11, and early | It is already required by an unrelated open item: the first embedding-model change invalidates every vector in both collections, and rebuilding from Postgres is the only path forward. Building it while the corpus is small means it is tested when running it is instant, rather than written under pressure when it is not. It also converts any future inconsistency from a debugging problem into a known recovery. |
| 2026-09-11 | The transactional outbox is built **now**, not deferred | Recommended for later (A+B+D was judged ~95% of the protection for ~20% of the work) and taken now instead. The deciding argument: the outbox table *is* the reconciliation list, so it removes the periodic scan rather than adding to it, and correctness that is structural does not need to be re-argued when the corpus grows. Accepted cost: a worker process with retry/backoff. |
| 2026-09-11 | [BUILD-PLAN.md](BUILD-PLAN.md) amended — §3.2 (invariants), §4.2, §4.3, §4.6, §7 | Logged here because the plan is only amended on a genuine change of direction, and the three resolutions above change its core logic rather than clarifying it. The original unresolved text is not preserved in the plan; it is preserved in P9, P10 and P11 below, which remain as written. |
| 2026-09-11 | **Embeddings are self-hosted sentence-transformers**, run as a container in the existing stack rather than called through the LiteLLM gateway | The embedding call is the highest-volume model call in the system — roughly 20 candidates on every field request, versus a handful of LLM calls only on a cache miss. Self-hosting removes both the per-call cost and the network round-trip from the hottest path, and fits the same self-hosting reasoning already applied to Qdrant. Accepted risk: smaller models are weaker on exactly the polysemy separation P4 depends on, which is why the next row exists. |
| 2026-09-11 | **The specific embedding model is chosen by measurement, not reputation** — the W3 calibration harness runs its sweep across 2–3 candidates (`all-MiniLM-L6-v2` 384d as baseline, `bge-base-en-v1.5` 768d, `e5-base-v2` 768d) and the one that best separates the collision pairs wins | The harness already computes a pairwise similarity matrix over hand-labelled pairs; running it across several models costs one extra loop. Since the model has to do one specific job — keep "Stack" (tech stack) away from "Stack" (data structure) — measuring it on that job is strictly better than picking on general benchmark reputation, and it produces a defensible answer to "why this model". Dimension is fixed at Qdrant collection creation, so this must settle before the collections are defined. |
| 2026-09-11 | **Feed delivery is cursor-free pagination with client prefetch**: a page of ~10 scrolls, with the client requesting the next page when ~3 remain | Matches how the product is actually used — a scroll feed, not a document. Keeps the client simple and the server stateless per request. |
| 2026-09-11 | **Refines (does not reverse) the stream-on-pass decision.** Transport-level streaming is dropped; on a cache miss the same paginated endpoint returns whatever has already cleared fact-check — possibly fewer than a full page — plus `generating: true`, and the client re-requests on a short interval until the flag clears | The original decision's requirement was *don't make the user wait for the whole batch*, and that is preserved exactly; only the granularity changes, from instant to one poll interval. What is bought: one transport instead of two, one endpoint shape for both the hit and miss cases, no SSE ingress upgrade handling. The deciding concrete factor is the mobile client — **React Native has no native `EventSource`**, so SSE would need a polyfill there while polling is an identical `fetch` on both platforms. Accepted cost: cards appear up to one poll interval late during a cold start. |
| 2026-09-11 | **Views are logged on display, never on fetch** | Prefetch guarantees the two diverge — the client holds up to a page of cards it has not shown. Logging on delivery would record impressions that never happened, in the one dataset that cannot be rebuilt. Written into the API contract as an explicit client obligation rather than left as an implementation detail, because it is invisible until the data is already wrong. See P12. |
| 2026-09-11 | **End-of-field card.** When a user has viewed every scroll in a field, the feed ends in one terminal scroll carrying the boundary plus three actions: generate more topics, revise what you have seen, or jump to an adjacent field | The boundary is stated rather than hidden. A feed that silently starts repeating is the engagement mechanic streaks were excluded to avoid (P8), so the loop is offered as a choice instead of applied as a default. Putting all three continuations on one card means exhaustion becomes a decision point rather than a dead end, and it is also where the product's revision half genuinely begins — "you have seen all of this before" is the exact condition under which re-exposure stops being filler. |
| 2026-09-11 | **Topic expansion is user-triggered, never automatic** | Removes the objection that killed automatic expansion: cost is only incurred when someone explicitly asks for more, rather than for every user who reaches the end of a field. Converts an unbounded background expense into a per-tap one. |
| 2026-09-11 | **Expansion re-runs the candidate generator with existing topics passed as exclusions** | Aims the generator deeper into the field's tail instead of having it re-propose what already exists and discarding the overlap. Better yield per call. Accepted costs, both knowingly: the prompt grows with the field's topic count, and it reaches the weaker long-tail topics faster than blind regeneration would. A cap on the exclusion list is available as a safety valve but is not needed at realistic field sizes. |
| 2026-09-11 | **Revision mode resurfaces viewed scrolls oldest-viewed first**, as an explicit mode rather than a silent continuation of the feed | `viewed_at` is already recorded, so the ordering costs nothing. Oldest-first approximates spaced repetition without building a scheduler — the real confidence-based version stays deferred, and this does not pretend to be it. |
| 2026-09-11 | **Adjacent fields: shared-topic overlap first, LLM suggestion to fill** | Overlap via `Field_Topic` is one SQL query, zero cost, zero latency, and grounded in real content the system already has — a third use of the junction table. Its limit is that it can only suggest fields someone has already requested, which is useless on a thin corpus, hence the LLM fallback. **Known risk:** an LLM-suggested field has no content by definition, so tapping it lands the user in a full cold start. That is the experience the partial-page design already handles, but the two kinds of suggestion should be distinguishable in the UI so the user is not surprised. |
| 2026-09-11 | **Cold start renders partial cards immediately; the waiting state appears only when the user exhausts them** | The user reads card 1 while cards 2–10 generate, so perceived cold start collapses from "time until a full page" to "time until the first card". A waiting indicator shown before that point would be overpromising against a pipeline with no bounded completion time; shown after, it is simply accurate. It carries the ready-count from the `generating` response at no extra cost, rather than being a bare spinner. |
| 2026-09-11 | **Outbox dead-letters after bounded retries, and the reconciliation sweep re-enqueues failed rows** | Makes the two consistency mechanisms layer instead of duplicate. The outbox is the fast path; when a row exhausts its retries, reconciliation still finds "topic in Postgres with no vector" and repairs it on its own schedule. The outbox failing permanently degrades to the safety net rather than losing the topic. Unbounded retry was rejected because a genuinely poisoned row — malformed payload, or a dimension mismatch after a model change — would spin forever and surface only as a worker that never catches up. |
| 2026-09-11 | **`Rejected_Draft` keeps the last N=5 rejections per topic**; `Topic_Generation_Stats` counters are kept forever | The cap bounds a text table whose value is diagnostic and local — you read rejections when investigating a rate, and a topic generates roughly 3–8 drafts, so five retains about one full run's worth. What the cap costs is the time-series shape, which is why the counters are kept indefinitely: they are tiny, and they are what would reveal a fact-checker drifting stricter over months. |
| 2026-09-11 | **REVERSES the earlier decision that nothing reads the view log in v1.** The feed now defines "the next page" as scrolls this user has not yet viewed — `User_View` is the paging mechanism | Paging by exclusion is what a scroll feed should do: no repeats across sessions or devices, no client-persisted position, no cursor to invalidate when a field gains new topics. The earlier decision (see the 2026-09-11 row beginning "Log every card view from day one") justified the log on the grounds that history cannot be backfilled; that reasoning is unaffected and still holds. What changes is that the log is no longer write-only, so **its health is now load-bearing for feed correctness** — a failed view write means the user re-sees a card. That is a new risk the write-only version did not carry, accepted knowingly. |
| 2026-09-11 | **Quarantine cap raised from N=5 to N=20** rejections per topic (migration `002`) | Chosen after verification check 8b showed that rejections written in one transaction share a `now()` timestamp, so a cap reached inside one run keeps an arbitrary subset. A higher cap keeps a single run from ever reaching it. **Corrects an estimate in the N=5 row:** that row says a topic generates "roughly 3–8 drafts". The card-generation prompt caps output at 4 cards per run, so the real ceiling is 4 rejections per run. The estimate was never checked against the prompt it described. |
| 2026-09-11 | **PARTIALLY REVERSES the no-retry decision** (see the rows beginning "Fact-check failures are deleted outright" and "The no-retry decision is not reversed"). A topic that comes back `empty` is **reported to the user as failed** (`failed_topics` in the feed response) and **retried on a later request**. | Within a run nothing changes: a failed draft is quarantined and never retried. What changes is that a topic whose entire run produced nothing gets another run later. Two reasons. Surfacing the failure is more honest than silently omitting a topic the user may have expected. And one failed run is weak evidence that a topic is unwritable, since a later scrape can find different sources and model output varies run to run. **Accepted cost:** no attempt limit, so a topic that can never pass is retried indefinitely. Made observable by the next row rather than prevented. |
| 2026-09-11 | **`topic_generation_stats.runs` counter added** (migration `003`) | The retry above has no attempt limit, so its cost has to be visible: runs > 1 means a topic came back empty at least once. Without the counter, a topic that can never pass burns a full pipeline run per request and nothing reports it. This is P10's lesson, "fail fast needs a counter", applied to the retry that followed from it. |
| 2026-09-11 | **Migration runner kept hand-rolled, with a Postgres advisory lock** serialising concurrent runs | ~70 lines, forward-only, no dependency, and verified repeatable. The one real gap against a library was concurrency: two Kubernetes replicas starting at once in W7 could both apply the same file. `pg_advisory_lock` closes that gap in one line. A second runner blocks until the first finishes, then finds nothing pending. `node-pg-migrate` was the alternative and was declined, since the only thing it would add that's needed here is the lock. |
| 2026-09-11 | **An empty topic is retried only when candidate generation proposes it again**, from a new field request or an expansion. Paging and polling never trigger a retry. | Treating `empty` as a plain miss would re-run the full pipeline on every poll. A single user waiting on a cold field could trigger dozens of runs a minute for a topic that keeps failing. Tying the retry to candidate-generation events means it only happens when something has actually asked for the topic again. Rejected alternatives: a 10-minute debounce, which is server-side and simple but retries on a timer rather than on intent; and a client-sent "fresh session" flag, which would turn any client bug that set it on every poll into an unbounded cost bug. |
| 2026-09-11 | **A failed topic is dropped for the current run and retried on the field's next generation run.** In practice that is the next "more topics" tap, which re-queues the field's failed topics alongside new candidates. Another field's candidate generation proposing the topic first also triggers a retry. | Closes the gap the previous row left. Expansion passes a field's existing topics as exclusions, so without an explicit re-queue a topic that failed in a field could never be retried there, and the `failed_topics` message would promise a retry that never came. Dropping the topic for the current run means paging and polling trigger nothing. Retrying on the next run keeps the promise true, and the cost still only follows a deliberate user action. See P17. |
| 2026-09-11 | **REVERSES the data-model decision to store saves as an array** ([_plan.md](_plan.md) §6.2: `Account { id, email, saved_scroll_ids[] }`). Saves now live in a `saved_scroll (account_id, scroll_id, saved_at)` table with real foreign keys (migration `004`). | The array had two flaws. Postgres cannot foreign-key into an array, so invariant 8 (no dangling saves) could never be enforced by the database. And the array has no timestamp, so the "newest first" order promised for `GET /v1/saves` depended on array order never changing, which nothing guaranteed. The table fixes both, and its primary key makes saving idempotent. Reversing it now costs nothing, because nothing has been saved yet. The API still returns a list of IDs, so the client's local mirror is unaffected. See P18. |
| 2026-09-11 | **Embeddings image pinned to `text-embeddings-inference:cpu-1.9.3`**, replacing `cpu-1.5` | `cpu-1.5` could not download any model: its bundled `hf-hub 0.3.2` cannot follow the relative redirects Hugging Face now uses for every model file (P19). 1.9.3 was tested in a throwaway container, where it downloaded and served `bge-base-en-v1.5`. It is pinned to the exact version, and explicitly **not** `latest`, because the calibrated similarity threshold is only valid for vectors produced by one exact runtime. An image that changed on a future pull would silently invalidate it. Things learned from the test run: on CPU it uses an ONNX backend, it caps batching at 8 concurrent requests, and the first model download took **329s**, cached in a volume afterwards. Rejected: keeping 1.5 and downloading the model separately with Python, which adds a setup step to every fresh clone, and writing our own embedding server, which is more code to own and batches worse. |
| 2026-09-11 | **Cards are retired, never deleted.** `scroll.retired_at`, a `live_scroll` view that every read path must query, and a trigger that rejects any scroll delete (invariant 12, migration `005`). | Check 9d showed that deleting a viewed card was already impossible, because the cascade into `user_view` hit the append-only trigger. The choice was between letting deletes erase view history (the one dataset that cannot be rebuilt) and never deleting. **Why a view here, when a flag on `Scroll` was rejected for the quarantine:** rejected drafts were never served, so nothing references them and they could live in their own table. A retired card *was* served, and it has views and saves pointing at it, so moving it out of `scroll` would break those foreign keys. The forgotten-`WHERE` risk is the same, and the view is what contains it, because the safe query becomes the default one. Decided now rather than when flagging is built, because W2 is about to write every read path. |
| 2026-09-11 | **Account erasure goes through one named, audited path**: `erase_account()` (migration `006`). The append-only view log permits deletes only during an erasure, and a raw `DELETE FROM account` is rejected (invariant 13). | Check 9e showed that an account with any views could not be deleted, which would have blocked data-erasure requests that data-protection law entitles people to make. Treating erasure as the one sanctioned exception keeps append-only absolute everywhere else. The trigger requires **both** the erasure flag **and** that the delete arrives as a cascade from the account. With the flag alone, code that set it could trim view history selectively while keeping the account. The audit row (`erasure_log`) records the time and row counts and **deliberately holds no identifier**, since one would defeat the erasure it records. Rejected: pseudonymising view history, which keeps per-user data this product has no use for once the user is gone and which timing patterns could re-identify. **Accepted residual:** these are guards against mistakes, not against a compromised application; database-role enforcement is a W7 task. See P21. |
| 2026-09-12 | **Migrations run automatically every time the serving service starts.** The container command is `node dist/db/migrate.js && exec node dist/index.js`, so the server only begins listening once the schema is current. | Chosen over a separate one-shot migrate job and over a manual step. `docker compose up --build` stays a single command, with nothing extra to configure and nothing for someone on a clean clone to forget. Accepted costs, stated when this was chosen: every restart of every replica runs the check (a no-op when nothing is pending, and the advisory lock queues replicas safely), and a failed migration stops the app from starting. Under Kubernetes that becomes a crash loop that looks like "the app is broken". That cost is mitigated rather than removed: every migration failure is logged with a `MIGRATION FAILED` prefix, so the first line of the failing container's logs names the cause. The README also mandates `--build`, because migrations ship inside the image and a stale image would apply an older schema while reporting success. See P22. |
| 2026-09-12 | **REVERSES the default LLM provider: Ollama on the host, not Gemini.** `qwen3:8b` as default, `qwen2.5-coder:7b` as fallback, reached through `host.docker.internal:11434`. | The gateway exists precisely so this is a config edit rather than a code change, and it was: one file, `services/llm-gateway/config.yaml`. ## Problems faced and fixed

Numbered sequentially, never renumbered. P1–P8 are problems designed out during planning, before any code existed — the reasoning is recorded because it is what shaped the architecture and would otherwise be unrecoverable from the code. P9–P11 were surfaced during this documentation pass and are **not yet resolved**.

### P1 — Scraping and serving content verbatim is a republishing problem *(planning, design trap)*
**Symptom:** The original concept was "scrape topics from the web and show them in the feed". Stated plainly, that is redistribution of other people's writing as the product's own content.
**Root cause:** Scraping was being treated as a *content source* rather than as a *grounding source*. The output of the scrape was going to be the output of the app.
**Fix:** Scraped text became input to the card generator only, never served text. What ships is generated prose plus the `source_url` that grounded it. The source link, originally conceived as a trust feature, doubles as attribution.
**Generalises to:** When a pipeline's input is someone else's property, the architectural question is not "do we cite it" but "does it ever reach the output at all".

### P2 — "Subconscious learning through scrolling" was a claim the design could not support *(planning, conceptual)*
**Symptom:** The founding pitch was that users would absorb concepts passively, the way they absorb memes. This is the fluency illusion: repeated exposure produces a feeling of knowing that is not retention.
**Root cause:** Conflating two distinct mechanisms — *exposure/priming* (real, weak, useful) and *learning/mastery* (real, strong, requires active recall). The product delivers the first and was claiming the second.
**Fix:** Two changes, one to the claim and one to the build. The claim narrowed to priming and revision, with an explicit "what this is not" boundary. The build gained a **tap-to-reveal recall prompt on every card**, moved into the MVP specifically because without any active-recall element the revision half of the claim stays aspirational.
**Generalises to:** When a critique lands on a product claim, the fix is usually part positioning and part feature. Changing only the wording leaves the product still unable to do what it now more modestly claims.

### P3 — A per-field cache regenerates identical topics for every field *(planning, design trap)*
**Symptom:** "HashMap" requested under *Java Utils* and again under *Java Collections* would run the entire scrape → generate → fact-check pipeline twice, producing two near-identical topics with separate cards.
**Root cause:** Topic identity was implicitly owned by the field that created it, so the cache key was `(field, topic)` rather than `topic`.
**Fix:** Topic decoupled from Field entirely, joined by a `Field_Topic` many-to-many junction table. The cache is checked per *topic name*, before generation. On a hit, one junction row is written and the existing scrolls surface under the new field at zero generation cost.
**Generalises to:** When the same expensive artifact keeps being produced twice, check whether the cache key contains something that is not actually part of the artifact's identity.

### P4 — Name-embedding similarity is not concept equivalence *(planning, latent)*
**Symptom:** The reuse mechanism from P3 matches candidate topic names by embedding similarity. "Stack" under a Web Development field means a technology stack; "Stack" under a DSA field means the data structure. Identical string, near-identical embedding, unrelated concepts — and the system would merge them.
**Root cause:** Embedding proximity of *names* was being used as a proxy for identity of *concepts*. For polysemous terms the proxy is simply wrong, and the two error directions are asymmetric: a false merge silently corrupts what a field serves and produces no error anywhere; a false split just regenerates something, costing money and nothing else.
**Fix:** v1 uses a strict threshold and no disambiguation stage, deliberately biased toward false splits. The correct two-stage solution — coarse retrieval by name, then a disambiguation check (description-embedding comparison or an LLM confirming genuine equivalence) before reuse is permitted — is fully specified in [BUILD-PLAN.md](BUILD-PLAN.md) §4.2 and deferred until bad merges are actually observed on real data.
**Generalises to:** When two failure modes have wildly different costs, tune toward the cheap one and defer the machinery that would fix the expensive one until you have evidence it occurs.

### P5 — The one-page format breaks for topics with real nuance *(planning, assumption)*
**Symptom:** "One topic, one page" holds for HashMap. It does not hold for anything requiring multi-step reasoning; such a topic either gets truncated into something misleading or silently stops fitting the format.
**Root cause:** A format constraint was being treated as universal when it is a property of a particular class of topic.
**Fix:** That class is declared out of scope for v1 and pushed to a later phase, rather than accommodated badly.
**Generalises to:** A format that only works for part of your content is a scoping decision waiting to be made explicit. Making it explicit is cheaper than discovering it card by card.

### P6 — No prerequisite model means advanced cards can precede basic ones *(planning, design trap)*
**Symptom:** A flat, field-scoped feed can surface a concept before the concept it depends on.
**Root cause:** There is no dependency graph between topics, and the streaming design (cards appear as they clear fact-check) makes ordering non-deterministic even if one existed.
**Fix:** Not fixed — deliberately deferred, and this is precisely why the product's scope narrowed to priming and revision (P2). For a *revision* tool, where the user has already met the material once, ordering matters far less than it would for first-time instruction. The scope narrowing is what makes the deferral defensible rather than merely convenient.
**Generalises to:** A deferred problem is only safely deferred if the scope still makes sense without it. Check that the narrowing actually covers the gap instead of hiding it.

### P7 — View history is the one dataset that cannot be backfilled *(planning, latent)*
**Symptom:** Every retention feature on the roadmap — spaced resurfacing, coverage map, weekly recap, confidence-based scheduling — needs a history of what the user has seen. If logging starts when the first such feature is built, every user's prior history is gone permanently.
**Root cause:** Treating the view log as a feature (build it when something reads it) rather than as infrastructure (build it before anything reads it).
**Fix:** `User_View { user_id, scroll_id, viewed_at }` is written from the first working feed, with no UI and no reader. Classified in [BUILD-PLAN.md](BUILD-PLAN.md) as an architecture decision, not a feature.
**Generalises to:** Distinguish data you can compute later from data you can only capture live. The second kind has to be written before you know what it is for.

### P8 — Streaks would contradict the project's own reason for existing *(planning, conceptual)*
**Symptom:** Streaks and daily goals appeared in the feature brainstorm as obvious inclusions, because every comparable app has them.
**Root cause:** Pattern-matching against the competitor set. The project exists partly to reduce the author's dependence on engagement-loop apps; importing the engagement loop reproduces the thing being escaped, pointed at nicer content.
**Fix:** Explicitly excluded and recorded as excluded, with the tension written down, so that any future addition has to argue past this entry rather than slide in as a default.
**Generalises to:** Features that "every app like this has" deserve more scrutiny than novel ones, not less — familiarity is not a rationale, and it is the easiest way for a product to drift away from its own premise.

### P9 — The lookup embeds a bare name but the index stores name + description *(2026-09-11, latent — NOT YET FIXED)*
**Symptom:** Surfaced while writing [BUILD-PLAN.md](BUILD-PLAN.md) §4.2, before any code exists. The Topic-Name Vector DB is specified as storing `{ topic_id, name+description embedding }`. But the Candidate Topic Generator outputs *names only*, so at lookup time the query vector is an embedding of a short string being compared against vectors of a string plus a paragraph.
**Root cause:** The write path and the read path of the same index were specified separately and never checked against each other. The index was designed around what is known at *topic creation* time; the lookup is constrained by what is known at *candidate generation* time, and those are not the same information.
**Fix:** Unresolved. Three options, none yet chosen: (a) index the name embedding alone and keep the description for a later disambiguation stage, (b) have the candidate generator emit a short description alongside each name so the comparison is symmetric, (c) store both vectors per topic and query the matching one. Option (b) also supplies exactly the input the deferred P4 disambiguation stage would need, which makes it the most likely choice — but it adds tokens to the highest-frequency LLM call in the system, so it is a real trade, not a free one.
**Blocking:** the similarity threshold cannot be calibrated until this is settled, because asymmetric comparison depresses scores and a strict threshold is exactly where that bites.
**Generalises to:** An index is a contract between a writer and a reader. Specify both sides together, and state what is available at query time before deciding what to store.

### P10 — Delete-on-fail can produce a topic with zero cards, invisibly *(2026-09-11, latent — NOT YET FIXED)*
**Symptom:** Not yet observed — no pipeline exists. Follows directly from two decisions taken together: fact-check failures are deleted with no retry, and a topic's cards are generated independently. If every draft for a topic fails, the topic exists with zero scrolls and simply never appears in a feed.
**Root cause:** The delete-on-fail decision was evaluated per *card*, where it is sound, and not per *topic*, where it can empty the whole thing. Nothing in v1 measures the rejection rate, so a systematically over-strict fact-checker would be indistinguishable from a system that is working — the feed would just be quietly thinner than it should be.
**Fix:** Unresolved, but cheap. Log pass/fail counts per topic from the first pipeline run, so the rejection rate is a number someone can look up, and treat "topic generated, zero cards survived" as a distinct, visible outcome rather than silence. This should land with the pipeline in phase P3 rather than after it. The retry decision itself is not being reversed — it is being made observable, which is what would justify reversing it later if the data says so.
**Generalises to:** "Fail fast and drop it" needs a counter attached, or you cannot tell a working filter from a broken one.

### P11 — Topic creation is a dual write across two systems with no shared transaction *(2026-09-11, latent — NOT YET FIXED)*
**Symptom:** Not yet observed. Creating a topic must write a row to Postgres and a vector to Qdrant. If the Qdrant write fails, the topic exists but is invisible to every future lookup — so it gets generated again on the next request, and again after that, with no error surfacing anywhere.
**Root cause:** An invariant ([BUILD-PLAN.md](BUILD-PLAN.md) §3.2, #5: every topic has exactly one vector) spans two stores that cannot participate in one transaction. The invariant is stated but nothing enforces it.
**Fix:** Unresolved. Minimum viable mitigation is a reconciliation query — topics in Postgres with no corresponding vector — run on a schedule or as a startup check, plus ordering the writes so the vector is written before the row is considered committed.
**Generalises to:** Every invariant that spans two datastores is a background job you have not written yet. Write down which invariants cross a boundary at schema-design time, while the list is still short.

### P12 — Prefetch would have silently corrupted the view log *(2026-09-11, design trap — designed out)*
**Symptom:** Not observed; caught while specifying the feed delivery model. The feed fetches a page of ~10 cards and prefetches the next page when ~3 remain. The obvious place to write a `User_View` row is where the scrolls are served, because that is where the server has them. That would record up to a full page of impressions for cards the user never saw — and if they abandon the session, never will.
**Root cause:** Conflating *delivered* with *seen*. They are identical in a request-response feed and permanently divergent in a prefetching one, and the prefetch decision was taken for UX reasons without anyone re-examining what "impression" meant afterwards.
**Fix:** Views are logged on display, written into the API contract as an explicit client obligation. The server does not infer impressions from what it sent.
**Why this one mattered more than it looks:** the view log is the only dataset in the system that cannot be reconstructed (P7), so this class of error is not detectable later and not repairable. It would have looked like working code producing plausible numbers, and every retention feature built on it afterwards would have been quietly wrong.
**Generalises to:** When a caching or prefetching layer goes in, re-examine every event that was previously logged at the boundary it now sits behind. The event did not change meaning because someone decided it should — it changed because the layer moved.

### P13 — The pagination model had no cold-start story *(2026-09-11, assumption — designed out)*
**Symptom:** The feed was specified as "request a page of 10 scrolls, prefetch the next page when 3 remain". For an uncached field there are no 10 scrolls, and there will not be for as long as the pipeline takes — a scrape plus several LLM calls per topic. Taken literally, the contract requires the server to block until a full page exists.
**Root cause:** The pagination model was designed against the steady state, where content already exists and the cache hit rate is high. The cold-start case is rare in aggregate but guaranteed for the first user of any field — including every user of a brand-new system, which is the state the product launches in.
**Fix:** The page endpoint returns whatever has cleared fact-check so far, even if that is two cards or zero, plus `generating: true`; the client re-requests on a short interval while the flag is set. One endpoint serves both cases. This preserves the intent of the original stream-on-pass decision — never wait for the whole batch — without adding a second transport.
**Generalises to:** A design validated against the steady state should be re-checked against the empty state. For anything that caches, the empty state is not an edge case — it is the state every user's first request lands in.

### P14 — The quarantine cap kept the oldest rows when timestamps tied *(2026-09-11, caught by tests)*
**Symptom:** The first run of `services/serving/src/db/verify-invariants.sql` failed check 8b: `FAIL 8b: tied timestamps make the cap keep arbitrary rows (kept d1,d2,d3,d4,d5)`. Seven rejections were inserted in one transaction, and the cap of 5 kept the five *oldest*. Each newer row deleted itself as it arrived.
**Root cause:** `rejected_at` defaults to `now()`, which is fixed for the whole transaction, so every rejection from one run gets the same timestamp. `ORDER BY rejected_at DESC LIMIT 5` over tied values falls back to physical row order, so the cap was choosing survivors by sorting on a column that isn't unique. Check 8a used distinct timestamps and passed, which is exactly why this would have shipped unnoticed.
**Fix:** Cap raised to 20 (migration `002`). In v1 a run produces at most 4 drafts, so one run never reaches the cap and the tie never decides anything. Each run is its own transaction with its own timestamp, so a newer run always outranks an older one. Check 8c asserts that and passes; all 14 checks pass. Accepted residual: once repeated retries push a topic past 20 rejections, the oldest retained run can be trimmed arbitrarily among its own tied rows. Ordering by a `bigserial` id would remove even that, and stays available.
**Also records a wrong claim.** When first reported, the tie was described as happening "in normal operation" and making implementation-plan test 4c.2 flaky. For v1 as it then stood, that was wrong: at most 4 drafts per run and one run per topic meant the cap of 5 could never be reached. The claim was made before checking the draft limit in the card-generation prompt.
**Generalises to:** A test that only uses distinct values will never find the bug that lives in ties. When a query sorts to pick survivors, test it with the collisions the column actually produces, which here means rows written in one transaction.

### P15 — A migration could be applied without being recorded *(2026-09-11, latent — designed out by review)*
**Symptom:** Found by reading the runner before it had ever touched a database. `001_init.sql` wrapped itself in `BEGIN`/`COMMIT`, and the runner executed the file and then inserted the `schema_migrations` row as a separate statement.
**Root cause:** The file's own `COMMIT` ended the transaction before the bookkeeping insert. A failure between the two would leave the schema applied but unrecorded, and every later run would fail with "relation already exists". The runner's own history would be what broke it.
**Fix:** The runner wraps each file and its bookkeeping row in one transaction, and migration files must not contain `BEGIN`/`COMMIT`; the rule is documented in the runner's header. Verified: on a fresh database, the first run applies, and the second reports `no pending migrations`. The advisory lock was added in the same pass. A runner started while the lock was held waited and finished in 7.6s, against about 1.4s unblocked. Two runners started together produced one `3 migration(s) applied` and one `no pending migrations`, both exited 0, and three rows were recorded.
**Generalises to:** When two writes must be atomic, check that nothing between them can end the transaction, especially code you pass through without reading, such as a SQL file executed as a string.

### P16 — Treating an empty topic as a miss would have re-run the pipeline on every poll *(2026-09-11, design trap — designed out)*
**Symptom:** Not observed; it follows from two decisions combined. The P10 fix made the lookup treat `status='empty'` as a miss, so a failed topic is not cached as a successful hit. A miss triggers the pipeline. Separately, a cold-start client re-requests the feed every few seconds.
**Root cause:** "Miss" had exactly one meaning, generate, and the P10 fix reused it without asking what else issues lookups. With polling in the design, a topic that always fails would be regenerated dozens of times a minute for one user, with no ceiling. The no-retry decision would silently have become retry-forever.
**Fix:** An empty topic is retried only when candidate generation proposes it again, never from paging or polling. A `runs` counter (migration `003`) makes repeated retries visible.
**Generalises to:** When a fix reuses an existing code path ("treat it as a miss"), list every caller that reaches that path. This fix was checked against the request that exposed the bug, not against the others.

### P17 — Expansion's exclusion list would have made failed topics unretryable in their own field *(2026-09-11, design trap — designed out)*
**Symptom:** Not observed; found while checking P16's fix against the expansion design. Expansion passes the field's existing topic names to the generator as exclusions, so that it aims deeper into the field. Failed topics are existing topics. And re-opening a field that already exists doesn't re-run candidate generation.
**Root cause:** The exclusion list was designed when every existing topic had content. The retry decision added a third kind, a topic that failed and is waiting for another attempt, and the exclusion list couldn't tell it apart from the rest. The `failed_topics` message would have promised a retry that no code path could deliver.
**Fix:** A failed topic is dropped for the current run and retried on the field's next generation run: tapping "more topics" re-queues the field's failed topics alongside the new candidates.
**Generalises to:** Adding a state to an entity invalidates every place that assumed its states were binary. Here, "existing" had silently meant "succeeded".

### P18 — Storing saves as an array meant they could be neither foreign-keyed nor ordered *(2026-09-11, design trap — designed out)*
**Symptom:** Found while writing `001_init.sql`. `account.saved_scroll_ids uuid[]` could not carry a foreign key, so invariant 8 (no dangling saves) went onto the list of invariants the schema does not enforce. Separately, API-CONTRACT.md promised that `GET /v1/saves` returns saves "newest first", and the array records no time at all.
**Root cause:** The data model was chosen at planning time as the simplest possible representation, "a simple array of scroll IDs", before the invariants or the API had been written. Two later documents each added a requirement the array couldn't meet, and neither was checked against the data model when it was written.
**Fix:** `saved_scroll (account_id, scroll_id, saved_at)` with foreign keys and a composite primary key (migration `004`), with any existing saves carried over in array order. Verified by check 9a (a save of a nonexistent scroll is rejected), 9b (a duplicate save is rejected) and 9c (deleting an unviewed scroll removes its saves); 17 of 17 checks pass. Check 9d, written alongside them, found a separate problem that "deleting a card removes its saves" had hidden; see P20.
**Generalises to:** When a later document adds a requirement, such as an invariant or an ordering promise in an API, check it against the data model the moment it's written. Here the invariant list and the API contract each quietly assumed a column the model never had.

### P19 — The embeddings image could not download any model *(2026-09-11, tooling)*
**Symptom:** The `embeddings` container exited with code 1 on its first start:
```
Error: Could not download model artifacts
Caused by:
    0: request error: builder error: relative URL without a base
```
**Root cause:** Hugging Face now answers every model-file request with a `307` redirect whose `Location` is a relative path (`/api/resolve-cache/models/…`). This was confirmed by requesting three of the model's files without following redirects: all three came back relative. The `hf-hub 0.3.2` library bundled in `text-embeddings-inference:cpu-1.5` can't follow a relative redirect. The log made it look as if only `config.json` failed. In fact the two files before it failed too, silently, because they're optional; `config.json` was just the first required one. Setting `HF_ENDPOINT` explicitly changed nothing (tested), which ruled out endpoint configuration.
**Fix:** Pin `cpu-1.9.3`. Verified in a throwaway container: it downloaded the model (`onnx/model.onnx` in 329s) and reached `Ready`.
**Generalises to:** A pinned dependency can break without changing, when something it talks to changes. And the first hard failure in a log isn't necessarily the first failure; check what failed silently before it.

### P20 — A card anyone had viewed could not be deleted *(2026-09-11, latent — caught by tests)*
**Symptom:** Check 9d, written alongside the saves checks, reported: `NOTE 9d: deleting a viewed scroll is BLOCKED - cascade hits the append-only trigger (user_view is append-only (invariant 7): DELETE is not permitted)`.
**Root cause:** Two rules that were each correct combined badly. `user_view → scroll ON DELETE CASCADE` exists so that views are never orphaned, and `user_view`'s append-only trigger exists so that history is never lost. The cascade turns a scroll delete into a `user_view` delete, the trigger forbids that, and the whole delete fails. It also meant that the argument for the saves table in P18, "deleting a card removes its saves", only held for cards nobody had viewed, which is almost none of them.
**Fix:** Cards are retired, never deleted (migration `005`). That adds `retired_at`, a `live_scroll` view for all reads, and a trigger that rejects every scroll delete with an explicit instruction. Verified: 9c (the delete is rejected with the retire message) and 9d (a retired card leaves `live_scroll`, and its 2 views and 1 save survive); 18 of 18 checks pass.
**Generalises to:** Check every `ON DELETE CASCADE` against the triggers on the table it cascades into, because each was written knowing only about itself. The same interaction also blocks account deletion; see P21.

### P21 — An account with any views could not be deleted, which blocked data erasure *(2026-09-11, latent — caught by tests)*
**Symptom:** Check 9e reported: `NOTE 9e: deleting an account with views is BLOCKED (user_view is append-only (invariant 7): DELETE is not permitted)`.
**Root cause:** The same combination as P20: `account → user_view ON DELETE CASCADE` plus the append-only trigger. It was found by applying P20's lesson to every cascade into `user_view`. The consequence was more serious than P20's: once a user had viewed a single card, there was no way to honour a request to erase their data.
**Fix:** Migration `006`. `erase_account()` sets a transaction-local flag for exactly one `DELETE`. The append-only trigger permits a delete only when the flag is on **and** the delete arrives as a cascade (`pg_trigger_depth() > 1`). A raw `DELETE FROM account` is rejected, and `erasure_log` records counts with no identifier. Verified by 10a (the account, 2 views and 1 save are removed and logged as (2, 1), and `erasure_log` has no identifier column), 10b (a raw delete is rejected), 10c (the flag plus a direct view delete is refused) and 10d (another account is untouched, and the flag is off again afterwards); 22 of 22 checks pass. Residual: these rules guard against mistakes, not against a compromised application; database-role enforcement is a W7 task.
**Generalises to:** When you find one bad interaction between a cascade and a trigger, list every other cascade into the same table, because they share the bug. Here exactly two foreign keys pointed into `user_view`, and both were broken the same way.

### P22 — The README's migration step had never worked *(2026-09-12, assumption — caught before anyone followed it)*
**Symptom:** The README said to run `docker compose exec serving npm run migrate`. Run inside the container, that failed with `sh: tsx: not found` and exit code 127. Separately, the running image contained only migrations `001`–`003`, because it had been built before `004`–`006` existed.
**Root cause:** Every migration during the build had been run from the host, where `tsx` (a development-only TypeScript runner) is installed. The production image compiles the TypeScript to JavaScript once and leaves development tools out, so the documented path had never been exercised. W1's done-condition, a clean clone reaching a running stack by following the README, had been assumed from runs on the host rather than tested. And because migrations ship inside the image, an image built before a migration was written applies an older schema and still reports success.
**Fix:** The container now runs `node dist/db/migrate.js && exec node dist/index.js` on every start (see the 2026-09-12 decision). Failures are logged with a `MIGRATION FAILED` prefix, and the README requires `--build` and has no manual step. Verified three ways. First, the rebuilt serving service logged `no pending migrations` and then `serving listening on :3000`, and all six migrations were in the image. Second, the image alone took an empty database to 12 base tables (`6 migration(s) applied`). Third, pointed at an unreachable database, the container exited 1 with `MIGRATION FAILED: getaddrinfo ENOTFOUND nohost-xyz` and never began listening.
**Generalises to:** A done-condition phrased as "from a clean clone" has to be tested from a clean clone. Every test run on the machine that built the thing inherits that machine's leftovers; here, a development dependency that the real path never gets.

### P23 — The model returned an empty reply, and thinking mode was rewriting the prompt *(2026-09-12, tooling — caught by a smoke test)*
**Symptom:** The first real call through the gateway to Ollama succeeded in 21s and returned **empty** `content`. Repeated with a larger token budget, the reply was `OK /think`, with the model's reasoning in a separate `reasoning_content` field and `completion_tokens: 70`.
**Root cause:** Two problems at once. `qwen3:8b` is a reasoning model whose thinking spends the token budget, so `max_tokens: 64` went entirely on reasoning and left nothing for the answer. And LiteLLM switches qwen3 into thinking mode by **appending `/think` to the user's message**; the model, asked to reply with exactly the text it was given, echoed the appended tag back. The second half is the more dangerous one: the prompt reaching the model is not the prompt that was written, it changes silently, and every prompt in this project demands strict JSON.
**Fix:** `think: false` on the qwen3 entry in `services/llm-gateway/config.yaml`. Verified from config rather than from a hand-written request: the same 64-token call that had returned empty now returns `OK` on 2 completion tokens, and a candidate-generator-shaped prompt returned parseable JSON with 2 topics and descriptions inside the length budget, in 3s on 39 tokens. Whether the fact-checker should get thinking back is deferred to W4.
**Generalises to:** When a smoke test returns an empty success, don't just retry it bigger and move on. Check what the client library actually sent. Here the library was editing the prompt, and no amount of care in writing prompts would have revealed it.

### P24 — Asking for JSON in the prompt was not enough *(2026-09-12, caught by a real run)*
**Symptom:** The first calibration run lost 2 of its 8 fields: `Web Development: FAILED - Bad control character in string literal in JSON at position 772` and `Marine Biology: FAILED - Expected ':' after property name in JSON at position 689`. The other six returned 20 clean candidates each.
**Root cause:** The client asked for JSON only in the prompt text. Nothing constrained the decoding, so the model emitted JSON-shaped text that was occasionally invalid — an unescaped control character inside a string, a missing colon. Six successes made the prompt look fine; the syntax was the problem. Worse than the 2-in-8 rate suggests: one of the casualties was **Web Development**, the field the calibration set most needed, because it is the designed source of the "Stack" collision.
**Fix:** `response_format: {type: "json_object"}` on every `completeJson` call, which LiteLLM maps to Ollama's JSON mode and constrains decoding, plus a repair pass that escapes raw control characters inside string literals as a second line of defence. Re-run: **8/8 fields, 156 candidates.**
**Generalises to:** If a model's output has to parse, constrain the decoding — a prompt is a request, not a guarantee. And when a partial failure happens, look at *which* items failed before deciding it was minor; losing a random 25% and losing the 25% your experiment depends on are different events.
