// microlearn — system architecture (v1 draft)

Field-scoped scroll feed · cache-then-generate agentic pipeline · split services · vector-DB dedup at generation time. v1 uses strict-threshold name-embedding matching only — a meaning-disambiguation step is added later only if bad merges actually show up on real data. Specific LLM/model choices and full tech stack are intentionally not decided yet.

Serving service

Feed Orchestrator

Receives a field-of-interest request. Coordinates candidate-topic generation, the cache lookup, and streaming scrolls back to the client.

Serving service · LLM agent

Candidate Topic Generator

In: a field name. Out: candidate topic names for that field — e.g. "Java Collections" → HashMap, TreeSet, LinkedHashSet…

Serving service

Account, Saves & View Logger

Login/signup. Reads/writes saved_scroll_ids[] on the account. Logs every scroll impression.

Decision · strict-threshold match

Topic-Name Vector DB Lookup

Embeds each candidate name, searches the Topic-Name Vector DB. v1: name-embedding similarity only — no meaning-disambiguation yet.

Match found

Reuse: Link + Serve

Adds a Field↔Topic link to the existing topic (no new row). Fetches its scrolls and streams them immediately — generation pipeline is never invoked.

Generation Pipeline Service — async, triggered on cache miss
Non-LLM · scraper / parser

Web Scraping Agent(s)

Pulls raw source material on the topic from the web. Out: scraped snippets + source URLs — kept as grounding context, never served verbatim.

LLM agent

LLM Data-Generation Agent

Generates supplementary explanatory content for the topic, filling gaps the scraped material alone may miss.

LLM agent

Card Generation LLM

Combines scraped + generated material, writes multiple one-page draft cards (scrolls) for the topic — original text, not republished scrape.

LLM agent

Fact-Check Agent

Verifies each draft card against the source material before it can reach a user.

Fail

Fails Check → Deleted

Card is discarded outright. No retry / re-queue in v1.

Pass

Passes Check → Persist + Stream

Saved and streamed to the client as soon as ready — no waiting on the rest of the batch. New topics get embedded into the Topic-Name Vector DB + linked to the field.

Data Stores
Relational DB

Core Tables

  • Field { id, name }
  • Topic { id, name, description }
  • Field_Topic { field_id, topic_id } — junction
  • Scroll { id, topic_id, content, source_url, trust_label }
  • Account { id, email, saved_scroll_ids[] }
Vector DB #1

Topic-Name Vector DB

{ topic_id, name+description embedding }

Used for: dedup / reuse check at generation time (strict threshold, v1).

Vector DB #2

Scroll-Content Vector DB

{ scroll_id, topic_id, content embedding }

Used for: semantic search, future "more like this" / recommendations.

View-tracking DB

User-View DB

{ user_id, scroll_id, viewed_at } — impression log. Foundation for any future resurfacing / spaced-repetition logic (not built yet).
