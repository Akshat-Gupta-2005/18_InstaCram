The only quality gate

Fact-Check Agent

Judges each draft against the gathered material. A source longer than one context window is chunked, never truncated — Ollama silently drops the front of an over-long prompt, where the card is (P33).

Per fragment: only contradiction is decisive. Silence never rejects.

An unrecognised verdict raises rather than defaulting to fail (P29).

The habit that runs through all of it

Every gate has a negative control

negative_control.py feeds the checker known-false cards. A 0.000 rejection rate and a blind gate look identical.

The rule: see it fail with the mechanism removed, or you have not tested it.

Read this before anything else: there is no arrow between Serving and Pipeline. The dashed amber pair through topic.status = 'pending' is the entire integration. Either service can be restarted, rebuilt or broken without the other losing a job — and that single fact explains most of the decisions below.

01High-level design

Three zoom levels: the system in its world, the pieces inside it, and where those pieces physically run.

1.1 Context — the system and everything outside it

Every external dependency except the two sources is local. No cloud LLM, no managed vector service, no analytics. The cost of a generated card is electricity — which is why measuring cost per topic was possible at all. The scraper identifies itself honestly, and the topic worker refuses to start without a contact rather than scraping anonymously.

1.2 Containers — what runs, and what each one owns

What to noticeWhy it matters
No arrow between serving and pipelineThe dashed pair through Postgres is the entire integration.
Both services talk to the same four thingsAnd both must agree on the embedded-text prefix and the match threshold. If they disagree, vectors written by one never match vectors searched by the other — silently. Hence the explicit forwarding in docker-compose.yml.
Qdrant is derivedDelete it and reindex rebuilds it. Nothing is designed as though the reverse were true.
Embeddings bypass the gatewayOne is a hot, small-model call; the other is slow and large. Routing both through one gateway puts the hot path behind the slow one's queue.

1.3 Deployment — where it physically runs today

Two processes are not containers, and both are easy to forget: Ollama and the Expo dev server. The browser calls the API directly, so the API's CORS list decides whether the app works. Three named volumes hold everything you would miss — database, vectors, and the cached model (a 289–329s download). docker compose down keeps them; down -v destroys all three. Only Postgres has a healthcheck others wait on — the rest are used lazily and retried.

02Low-level design

Inside each service: the modules, who calls whom, and the objects that carry the design.

2.1 Components — serving

The candidate generator lives here, not in the pipeline — it runs on every field request, including pure cache hits where no generation happens. embeddingText.ts is a contract, not a helper: the pipeline builds the same string in its own embedding_text.py, and if they drift nothing errors, the cache just stops finding things. repo/feed.ts reads only live_scroll, so a retired card cannot reach a user through a filter someone forgot.

2.2 Components — pipeline

lifespan is where P37 was. Both workers existed and neither ever started in the deployed service. They now start by default — a default of off would recreate the bug the first time someone deployed without the variable — and /health reports each by name. stores/qdrant.py never creates a collection, because a service that silently creates one with the wrong vector size turns a loud failure into a silent one.

2.3 Class — topic resolution, the branch the product rests on

DefenceWhat happens without it
Advisory lock on the candidate name8 simultaneous requests create 8 topics
Same-name read from Postgres8 duplicates again — Qdrant cannot see a topic whose vector the outbox has not written
Deterministic chooseMatchTwo fields link different copies, and the reuse guarantee quietly stops holding
Each row was seen failing with its mechanism removed (P35). The middle one is the valuable one: with the lock held the run took 1,433ms — the requests genuinely serialised — and still produced eight duplicates. That turned "a lock around a read of an eventually-consistent store serialises nothing that matters" from an argument into a measurement. beforeDecide exists only so a test can force eight requests to interleave inside the lock; concurrency that depends on the scheduler being kind is not a test.

2.4 Class — the client's feed state

Two rules of the API contract live in this one hook, and both corrupt data silently when broken: log a view on display, never on fetch (prefetch means the app holds cards nobody has seen), and poll at retry_after_ms. Three fields exist because of P38 — focused, flushViews(keepalive) and seenBefore. See §6.4.

03Data model

15 tables, one view, 12 forward-only migrations. What is stored, how it relates, and what crosses the wire.

3.1 Entity relationships

In the schemaThe decision it encodes
field_topic as a junction; topic.name_norm not uniqueA topic is not owned by a field, and duplicates are legal. The system prefers a wasted duplicate to a wrong merge.
topic.status = 'empty'A topic whose drafts all failed must be representable, or the cache re-serves it as a success forever.
scroll.retired_at + live_scrollA bad card disappears from every read while its view history survives. Deleting it would break the history.
user_view append-only, by triggerIt is the paging position and the only dataset that cannot be rebuilt. Convention would not be enough.
erasure_log with counts and no identifierProving an erasure happened must not re-create the data it erased.
Enforced by the database, not by code. Triggers block: updating or deleting a user_view; deleting a scroll anyone has viewed; rewriting a topic.description; deleting an account outside erase_account(). verify-invariants.sql tries to break each one and prints 22 PASS/FAIL checks inside a transaction it rolls back.

04Sequences

Six things that happen, in order. These are the diagrams to read when you want to know what actually runs on a tap.

4.1 Cold start — a field nobody has asked for

The user-facing request does four cheap database operations and returns. Everything expensive happens after it, in two workers that do not know about each other. Cards appear per topic, not per field, so a cold field becomes usable long before it is finished.

4.2 Cache hit — the whole thesis in one diagram

This is the acceptance test of the entire design (tests/reuse.test.ts), and it was seen failing with reuse disabled. The threshold 0.955 is deliberately strict: the lowest cutoff with zero false merges over 44 labelled pairs, keeping 67% reuse. The system would rather regenerate a duplicate than show you a card about the wrong thing.

4.3 Reading, paging and view logging — where the data is easiest to corrupt

There is no cursor. "The next page" means "cards this account has not viewed", so the view log is the pagination state. A lost view hands the same card out again; an invented view silently burns a card the user never saw. Both happened, and neither raised an error (P38).

4.4 "More topics" — the only user-triggered generation

Generation is never triggered by paging or polling — only by an explicit tap (P16, P17). topics_linked exists because a field can gain cards without generating anything, and without counting that, the action would be offered forever.

4.5 The outbox — why a vector write cannot lose a topic

Qdrant killed mid-drain was tested: the row retried, kept its error, the worker survived, and the vector appeared on restart. Stranded rows are reaped; rows that exhaust their retries are dead-lettered, and reconciliation then carries what the fast path gave up on.

4.6 Login

Before this existed, AUTH_MODE=dev trusted any bearer token as the identity, so a login screen on top of it would have been decoration. Google sign-in becomes a second branch yielding an identity into the same requireAccount. Known gaps: no rate limiting, and the web token lives in localStorage. This mode is for one machine and must be replaced before anything is network-reachable.

05State machines

Five things have states, and each state exists because collapsing it into another one caused a bug.

5.1 Topic — the most important three words in the schema

OutcomeWhat failedTopic left asDrafts quarantined?
unsourcedno source could ground itemptyno drafts existed
emptyevery draft was rejectedemptyyes, with reasons
degradedthe checker itself erroredpendingno
Collapsing these into "no cards" would report a 100% rejection rate for a broken gate and send someone to fix the generator — which is what P10 and P29 were about.

5.2 Field expansion — candidate generation as a job

A partial failure while resolving finishes the job rather than regenerating: 32–54s of LLM output has already been paid for, and throwing it away to retry one candidate is the expensive kind of tidy.

5.3 Outbox row — owed vectors

Reconciliation is asymmetric on purpose: a vector missing from Qdrant is re-enqueued (wasteful, safe); an orphan vector in Qdrant is deleted (a stale hit would be corruption).

waiting and finished look identical to a careless client — both are "no cards". That is why generating and exhausted are separate flags, and why an owed expansion counts toward generating.

06Decision flows

Four decisions, branch by branch. Each has a bug behind it: the shape of the flow is the fix.

6.1 The generation graph — five steps, one real branch, four endings

Why join exists (P30). LangGraph fires a node when any inbound edge fires, not when all of them do. With the branch hanging off scrape directly, routing to unsourced did not stop data_gen's edge from firing card_gen — so an ungrounded topic still produced cards, from LLM material with no source, and reported itself ready. Invariant 4 broken by orchestration while every agent behaved perfectly. Caught by a test written because the join semantics were uncertain, which asserts which steps did not run.

6.2 Topic resolution — the four outcomes

Each red box was seen failing with it removed (P35) — the table in §2.3 has the numbers.

6.3 Fact-checking a long source — chunked, never truncated

Why this shape (P33). Ollama defaults num_ctx to 4096 and silently truncates an over-long prompt from the front — where the card sits. The gate had been approving cards it was never shown: 11 of 20 in one run, stamped sourced_verified. Detection of planted errors went 0/3 → 7/7 once chunked, with faithful controls still passing. Only contradiction is decisive, because absence from one fragment is not evidence. And the two size budgets are separate (10,000 vs 4,000): a 10k excerpt diluted attention enough that the model called an inverted claim "supported".

6.4 Logging a view, client-side — where two silent bugs lived

Both red boxes are P38, found from one user report — "the deck always refreshes from 0". Without keepalive and the hidden-page flush, a refresh runs no unmount, the buffered view dies with the page, and the server correctly hands the same card back as card 01. Without the focus check, every feed screen ever opened stayed mounted — Esc pushed a new Home rather than going back — each keeping its keydown listener and display timer, so one press of J logged a card in every hidden copy. The log holds the same card eight times at an identical millisecond. Two faults, one append-only dataset, opposite directions, no error either way.
